# 菜谱内容扩充与年轻化界面设计

## 1. 背景与目标

当前项目已经具备“选择食材 → 匹配菜谱 → 查看详情 → 收藏/反馈 → 加入本周计划 → 生成购物清单”的离线主链路，但用户对“菜谱少”和“页面不年轻”的反馈反映出两个问题：

1. 本地菜谱只有 20 道，婴儿辅食、老年餐和家常菜内容偏少，且现有图片存在重复、错配和占位感。
2. 首页偏工具化，菜谱以长列表平铺；现有暖橙色方向正确，但页面缺少内容分组、轻量卡片和更明显的年轻交互节奏。

本次设计目标：

- 将本地菜谱从 20 道扩充至 30 道；
- 优先补足老年餐、婴儿辅食和家常菜，避免只增加同质化的低脂/高蛋白菜谱；
- 为 30 道菜提供一一对应的年轻食物插画；
- 采用已确认的 A 方案“活力橙绿”：保留品牌橙，加入草木绿和少量莓果色；
- 将首页从“筛选工具页”调整为“先做决定、再发现内容、最后使用工具”的菜谱发现页；
- 保留现有健康边界、收藏、周计划、在线扩展和本地数据能力，不在本轮引入拍照识别、云同步或真实采购计量。

## 2. 已确认的方案

### 2.1 内容规模

本地菜谱总数固定为 30 道，编号保持连续：`r001` 至 `r030`。

新增 10 道菜谱的初始内容规划如下：

| 编号 | 菜谱 | 主分类 | 重点场景 |
|---|---|---|---|
| r021 | 虾仁西兰花藜麦碗 | 健身餐 | 健身、白领午餐 |
| r022 | 香菇鸡丝拌面 | 家常菜 | 工作日晚餐、快手 |
| r023 | 豆腐蒸肉饼 | 老年餐 | 老年人、家庭共享 |
| r024 | 鳕鱼土豆泥 | 婴儿辅食 | 软烂、易吞咽 |
| r025 | 西葫芦鸡蛋软饼 | 婴儿辅食 | 手指食物 |
| r026 | 山药胡萝卜鸡肉粥 | 婴儿辅食 | 早餐、软食 |
| r027 | 番茄牛腩焖饭 | 家常菜 | 家庭一锅饭 |
| r028 | 清蒸南瓜鸡腿肉 | 老年餐 | 低油、软嫩 |
| r029 | 豆腐虾皮小白菜汤 | 老年餐 | 低脂、易咀嚼 |
| r030 | 紫薯燕麦酸奶杯 | 低脂餐 | 早餐、轻食 |

分类目标不是让每道菜只能属于一个类别，而是保证主分类分布更均衡：老年餐、婴儿辅食和家常菜各至少达到 5 道；健身餐、低脂餐和控糖餐继续通过 `suitableGroups`、健康标签和场景字段交叉覆盖。

新增菜谱所需但当前食材字典没有的食材，必须先加入 `src/data/ingredients.ts`，并为常见别名建立关键词，例如“西葫芦/角瓜”“牛腩/牛肉”“燕麦片/燕麦”“酸奶/无糖酸奶”。食材显示名、菜谱用料、忌口匹配和在线结果过滤必须使用同一套 canonical 归一化规则。

### 2.2 特殊人群数据边界

婴儿辅食和老年餐不能只靠标题表达适用范围。`Recipe` 类型增加可选字段：

```ts
interface Recipe {
  // existing fields remain unchanged
  allergens?: string[]
  ageRange?: string
  servingNote?: string
}
```

约束如下：

- 婴儿辅食必须填写 `ageRange`、`allergens` 和 `servingNote`；
- `servingNote` 只描述盐糖、熟度、去刺、切碎或观察过敏等操作边界，不写治疗或保证性承诺；
- 常见过敏原必须在详情页靠近用料和风险提示的位置展示；
- 营养值仍然是单份估算值，不能因为新增字段而被包装成医学建议；
- “温补、利水、补铁”等容易被理解为功效的文案应改为烹饪或营养事实描述；
- 详情页继续保留健康免责声明。

### 2.3 插画素材

统一采用年轻食物插画风，不再使用 loremflickr、猫雕塑、包装食品或与菜名无关的图片。

每道菜对应一个本地图片文件：

- 路径：`src/static/recipes/r001.jpg` 至 `r030.jpg`；
- 比例：3:2；
- 尺寸：800×533；
- 画面：明亮背景、盘中主体清晰、主要食材可辨识、主体位于安全裁切区域；
- 禁止：文字、水印、品牌标识、明显包装、与菜名无关的场景；
- 视觉：明快但不过度荧光，允许使用橙、草木绿、莓果红作为点缀；
- 资源必须唯一，不能通过复制同一图片填充多个菜谱槽位。

素材验收需要同时检查：菜名与画面匹配、卡片裁切后主体完整、详情页封面可读、文件命名与数据映射一致。图片加载失败时继续使用现有 fallback，不因素材问题导致页面空白。

## 3. 年轻化视觉系统

### 3.1 颜色角色

不整体替换品牌，而是调整颜色职责，避免所有主操作都使用沉重的深橙。

| 角色 | 建议色值 | 使用场景 |
|---|---|---|
| 活力橙 | `#F45B3C` | Hero、大面积品牌背景、重点视觉 |
| 深橙 | `#C83D2C` | 带白字的主 CTA，确保对比度 |
| 草木绿 | `#56A968` | 健康状态、已拥有食材、完成态 |
| 浅草木绿 | `#E4F5DF` | 健康卡片、低风险提示背景 |
| 莓果红 | `#D94B71` | 收藏、灵感、轻量强调 |
| 浅莓果 | `#FFE6ED` | 收藏/灵感标签背景 |
| 页面底色 | `#FFF9F3` | 页面背景，保留轻盈暖感 |
| 主文字 | `#24212A` | 标题和重要内容 |
| 辅助文字 | `#77737D` | 描述、说明、次要信息 |

带白字的按钮不得使用过浅的橙色作为唯一背景；必要时使用深橙填充或深色文字。选中态不能只依赖颜色，还要增加边框、勾选图标、文字或形状变化。

### 3.2 组件语言

- 保留圆角和 Lucide 线性图标，但减弱“纸张/杂志”语气；
- 全站统一使用无衬线字体和较粗的标题层级；
- CTA 使用清晰动词：`开始找`、`帮我选`、`加入计划`；
- 不使用 Emoji 或 Unicode 伪图标；
- 保留按压反馈、收藏心跳和轻量渐入；
- 列表渐入采用轻微透明度/位移变化，不使用会影响滚动性能的复杂动画；
- 所有页面继续为底部 TabBar 和安全区留出空间。

## 4. 页面结构设计

### 4.1 首页：从筛选工具改为内容发现页

首页按以下顺序组织：

1. **Hero / 今日灵感**
   - 日期、品牌标题和一句短文案；
   - 使用当天菜谱插画；
   - 显示“30 道本地菜 · 离线可看”；
   - 主操作是进入今日灵感详情。
2. **首屏决策入口**
   - `今晚吃什么`：从当前可用结果中随机选择；
   - `本周餐桌`：进入计划页；
   - 若存在来自空餐位的 handoff，显示“正在为周几早餐/午餐/晚餐选菜”，可取消定位。
3. **搜索入口**
   - 支持菜名、食材、标签和别名；
   - 搜索按钮使用深橙或符合对比度的渐变。
4. **内容集合**
   - `今日高匹配`：根据食材匹配度展示；
   - `20 分钟快手`：快速筛选；
   - `家常下饭`：以家常菜为主题；
   - `轻食与低负担`：以低脂、控糖、白领场景为主题。
   - 内容集合复用现有筛选和排序函数，不复制一套新的推荐规则。
5. **冰箱里有什么**
   - 顶部横向分类；
   - 下方自然展开的单一食材区域；
   - 已选食材、匹配数量和查看结果操作保持高可见；
   - 明确写出“选择任一食材即可匹配，已有越多匹配度越高”。
6. **结果列表**
   - 默认使用紧凑卡片；
   - 显示图片、菜名、用时、热量、匹配度和“已有/还需”；
   - 描述和反馈按钮下沉到详情或推荐页，避免首页卡片过长。
7. **在线扩展**
   - 继续作为次级区域；
   - 明确在线结果不参与健康推荐、只保存在本机；
   - 不恢复无法跨设备恢复的在线详情分享。

### 4.2 菜谱卡片

`RecipeCard` 保留一个组件，提供三种明确变体：

- `compact`：首页结果，隐藏长描述和反馈操作，突出快速比较；
- `recommendation`：健康推荐页，显示 1 条主要推荐依据和必要标签；
- `default`：收藏和其他场景，显示完整描述但控制卡片高度。

卡片信息优先级固定为：

```text
菜名/图片 > 用时与热量 > 匹配度或推荐依据 > 标签 > 次要描述/反馈
```

反馈行为不能阻止卡片主体点击进入详情；反馈按钮必须阻止事件冒泡并有明确选中状态。

### 4.3 推荐页

推荐页继续使用六类健康人群，但视觉上增加轻量图标或数量提示，不引入 Emoji。推荐结果卡显示：

- 当前人群；
- 命中的健康标签；
- 已排除的明确忌口；
- 一句诚实的推荐依据。

健康人群是推荐和风险提醒，不替代医生诊断。明确忌口仍然是硬过滤条件。

### 4.4 详情页

详情页调整为：

```text
封面与菜名
→ 用时/难度/热量
→ 健康与忌口风险
→ 加入本周计划
→ 用料与过敏原
→ 单份营养估算
→ 烹饪步骤
→ 小贴士与免责声明
→ 收藏/反馈
```

如果当前档案存在明确忌口或健康目标冲突：

- 风险在加入计划按钮前展示；
- 加入计划按钮改为“仍要加入计划”；
- 保存前再次弹出确认；
- 任何取消或保存失败都不得消费计划 handoff。

### 4.5 我的与本周计划

本轮主要做视觉统一和内容摘要，不重新设计业务模型：

- 我的页顶部显示当前健康目标、忌口数量、收藏数量和计划入口；
- 健康目标保留“不设置目标”；
- 清除数据继续放在低频数据管理区域；
- 本周计划突出今天、已安排餐次数和购物清单入口；
- 继续使用动态周日期和固定底部安全区。

## 5. 架构与数据流

### 5.1 数据边界

- `src/data/recipes.ts` 维护 30 道本地菜谱；
- `src/data/ingredients.ts` 维护本地食材与别名；
- `src/types/recipe.ts` 增加特殊人群可选字段；
- `src/utils/recipeFilters.ts` 继续提供 canonical 食材匹配、忌口硬过滤和健康风险判断；
- 页面只组合现有数据函数，不在模板中实现新的字符串包含判断；
- `src/static/recipes` 是唯一运行时菜谱图片来源；
- 收藏、计划、反馈和饮食档案的本地存储键保持兼容，不做数据迁移破坏。

### 5.2 内容集合计算

首页集合使用同一份经过饮食档案过滤和反馈排序的菜谱集合：

```text
recipes
→ canonical 忌口过滤
→ 反馈过滤/排序
→ 主题条件（用时、分类、健康标签、匹配度）
→ RecipeCard 变体
```

主题集合没有结果时显示现有 EmptyState，不使用虚假推荐或随机填充。

### 5.3 计划上下文

继续使用一次性内存 handoff：

```ts
{ date: string, meal: 'breakfast' | 'lunch' | 'dinner' }
```

计划页写入目标；首页显示并允许取消；详情页只读取并预选；只有 `saveMealPlanEntries` 成功后才消费目标。用户从首页正常浏览时不能继承旧目标。

## 6. 错误处理与内容校验

### 6.1 数据校验

扩展现有 `recipeDataValidation`：

- 菜谱 ID 唯一且完整覆盖 `r001`–`r030`；
- 每道菜至少有一个用料、一个步骤、合法营养值和图片路径；
- 图片路径与菜谱 ID 一一对应；
- 新增食材存在于食材字典或通过明确的 canonical 映射归一化；
- 婴儿辅食必须具备 `ageRange`、`allergens`、`servingNote`；
- 分类最低数量和重点人群最低数量满足本设计目标；
- `suitableGroups` 与 `avoidGroups` 不得产生自相矛盾的重复配置。

### 6.2 运行时降级

- 图片加载失败：显示菜名、主要食材和图标 fallback；
- 搜索无结果：显示调整关键词、放宽筛选或设置档案的操作建议；
- 计划保存失败：保留弹层和 handoff，提示重试；
- 在线服务失败：显示错误和重试，不影响本地 30 道菜；
- 在线缓存失效：显示“仅本机缓存已失效，请返回首页重新查询”；
- 任何健康提示都不能隐藏风险来源或暗示医学保证。

## 7. 测试与验收

### 7.1 自动化测试

必须更新或新增：

- `src/utils/recipeFilters.test.ts`
  - 新增食材别名匹配；
  - 子串误判边界；
  - 忌口硬过滤；
  - 健康目标风险提醒。
- `src/utils/recipeDataValidation.test.ts`
  - 30 道菜 ID 完整性；
  - 分类数量；
  - 图片路径唯一性；
  - 婴儿辅食安全字段。
- `src/utils/recommendHandoff.test.ts`
  - 目标预览、取消、消费时机。
- 若主题集合抽成纯函数，增加对应集合过滤和空结果测试。

交付前运行：

```bash
npm ci
npm test
npm run typecheck
npm run lint
npm run build:mp-weixin
npm run build:h5
```

### 7.2 微信开发者工具验收

使用 `dist/dev/mp-weixin` 或 `dist/build/mp-weixin` 验收：

1. 首页 Hero、橙绿配色、内容集合和底部安全区；
2. 30 道菜能够通过搜索、分类和主题集合被发现；
3. 新增菜谱图片与菜名匹配，图片不重复；
4. 别名搜索和忌口过滤结果一致；
5. 设置/取消健康目标后首页、推荐页、详情风险提示同步；
6. 空餐位 → 首页显示目标餐次 → 详情预选 → 保存成功后回到计划；
7. 取消或保存失败不会消费目标；
8. BottomSheet 内容过长时可以滚动，快速关闭后重新打开不被旧定时器隐藏；
9. 收藏、反馈、计划和购物清单仍可用；
10. 在线服务不可用时，本地菜谱仍正常工作。

## 8. 非目标与后续方向

本轮不实现：

- 拍照识别食材；
- 登录和云同步；
- 真实采购重量、家庭人数和库存扣减；
- 在线菜谱跨设备分享；
- 推荐模型的机器学习化；
- 大规模页面拆分或重写路由架构。

这些方向应在 30 道本地内容、素材质量和主流程稳定后单独立项。

## 9. 完成标准

本设计完成后，用户应能感受到：

- 菜谱从 20 道增加到 30 道，重点分类不再明显偏空；
- 每张图片都是真正对应菜名的年轻食物插画；
- 首页先帮助用户做决定，再引导发现菜谱，最后提供筛选和计划工具；
- 橙色、绿色、莓果色各自承担明确角色，页面更轻快但不丢失健康产品的可信度；
- 原有离线主链路和健康边界不被破坏；
- 自动化检查和微信开发者工具验收均有可复现证据。
